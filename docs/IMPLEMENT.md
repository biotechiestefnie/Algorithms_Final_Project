### Project Snapshot

**Research Question:**

How much Markov “memory” is required for Markov Chain model to
faithfully delineate between coding regions (Exons), noncoding regions
(Introns), promoters, and repetitive elements within the human genome?
Understanding the relationship between structural signal complexity and
Markov memory is biologically meaningful and algorithmically valuable
because it can yield insight on:

    * How simple or difficult it is to detect genomic functional elements with this computational approach
    * Where the model breaks down for each functional class
    * How memoization influences overfitting versus overgeneralization within each class
    * Which biological signals are localized and which are long-range
        * A biological class is local if the information needed to recognize it is contained in short, contiguous
          patterns. These would be signals that a low-order Markov chain (small k) should reliably recognize
        * A biological class is long-range if the information needed required for detection spans dispersed
          patterns, and features extending beyond a few nucleotides. Such classes require higher Markov memory
          (larger k) to effectively distinguish

**Algorithm:**

The successful completion of multiple genome sequencing projects paired
with significant advancements in Next Generation Sequencing (NGS)
technologies has generated an unprecedented wealth of genomic data,
providing a rich substrate for computational analysis and scientific
discovery. Markov chains form a fundamental class of probabilistic
models that have become indispensible tools for investigating a wide
range of bioinformatics problems, from gene prediction to protein
structual analysis. They are underpinned by a robust mathematical
framework that can be exploited to capture the dynamic dependencies
between adjacent nucleotides while simultaneously simulating their
structural characteristics (Ma et al., 2025), making them inherently
well-suited for extracting meaningful insights from complex biological
sequences.

A key consideration of Markov applications is the Markov property, which
asserts that the next state depends only on a limited number of previous
states. While this assumption simplifies computation, it also imposes a
“memoryless” constraint that can be limiting for biological sequences,
which frequently contain motifs, periodicities, and regulatory signals
that extend beyond a single nucleotide of context (Ryabco & Usotskaya,
2008). To address this, higher‑order Markov models incorporate a longer
history by conditioning on the previous k nucleotides. And while
increasing k allows the model to uncover richer local dependencies and
more biologically meaningful patterns, it also expands the state space
exponentially (4^k), requiring substantially more data to estimate
accurate transition probabilities in addition to an ultimately
unrealistic computational investment (Burkes & Azad, 2020).

This trade‑off between contextual richness and data sparsity makes the
choice of k a central modeling decision. If k is too small, the model
fails to capture important structural features; if k is too large, the
model becomes unstable, overfits, or collapses due to insufficient
observations. Understanding how Markov memory interacts with the
complexity of biological signals is therefore essential for determining
when these models are applicable, where they break down, and how much
context is required for reliable structural discrimination in the
genome.

For this study, I implement deterministic k‑order Markov chains,
training one model for each genomic structural class to learn
characteristic transition probabilities over increasing orders of k.
Each model estimates the likelihood of a sequence by evaluating the
conditional probability of a nucleotide given the previous k nucleotides
and accumulating these probabilities in log space. By systematically
increasing the Markov order and evaluating classification performance
across promoters, introns, exons, and repeats, the study directly
measures how much contextual memory is required for faithful recognition
and identifies the precise moment at which the models begin to fail and
why. These insights can help pave the way for more successful future
applications of Markov models in genomics, informing the design of more
sophisticated models that balance context and complexity.

*Current Implementation Status:*

The full pseudocode outlined in the Conceptual Progress Report has now
been implemented. Most critically, this includes the preliminary version
of the Markov model, which serves as the core algorithmic component of
the project. The main implementation resides in src/markov_model.py,
designed as an importable module executed from within the Jupyter
Notebook run_markov_pipeline.ipynb. This notebook functions as the
primary driver for the entire pipeline, coordinating data loading, model
training, evaluation, and results reporting. Its structure supports
iterative development, allowing me to refine the implementation as I
examine preliminary outputs, adjust parameters during the prototype run,
and thoroughly document each step, including mitigation strategies and
justifications for all modifications.

The raw data extraction phase unexpectedly became a test of resilience
and problem‑solving. After successfully retrieving 1,796 high‑quality
promoter annotations aligned to the hg19/GRCh37 assembly, I discovered
that UCSC had removed exon and intron FASTA export functionality for
hg19/GRCh37 after 2023, leaving only limited annotation downloads and no
sequence‑level extraction options. This forced me to redesign the entire
extraction workflow: instead of relying on UCSC’s direct FASTA exports,
I had to reconstruct exon and intron sequences manually using the genome
FASTA and GENCODE v19 annotation files. As a result, extracting raw
sequences for all four structural classes—followed by filtering, random
sampling, and constructing both positive and negative prototype
datasets—expanded into a substantial task of its own. To prevent this
extensive data‑preparation process from overwhelming the model pipeline
narrative, I separated the workflows by creating dedicated executables
and a standalone Jupyter Notebook specifically for data collection,
preprocessing, and preliminary analysis. This ensures that the model
implementation and evaluation remain the primary focus of the project,
while the data preparation steps are still documented in full detail.

During implementation, several deviations from the original pseudocode
became necessary. The most significant change involved restructuring the
program design for the model from a main executable script into modular
Python files that include:

    * data_loading.py 
    * markov_model.py
    * train_model.py 
    * classify.py 
    * reporting.py

All of which are designed to be imported for execution into the model
pipeline Jupyter Notebook, which is now the primary driver program for
the model. This allowed for clearer separation of steps and
significantly simplified debugging during the prototype phase.

Additionally, I implemented a comprehensive and exploratory data
extraction and preparation workflow with separate scripts and a
dedicated Jupyter Notebook to execute and document all steps,
improvisions, insights, class characteristics, justifications, and
preliminary analyses in preparation for the prototype run. This workflow
was necessary to overcome the unexpected challenges of raw data
retrieval and to ensure that the model implementation and evaluation
remain the central focus of the project. This was a critical decision
and a major deviation from the original design of the study, but it was
absolutely necessary to maintain the project centered upon model
implementation and evaluation, while still including a thorough and
transparent documentation of the data preparation process for
reproducibility.
